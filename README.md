# code-with-quarkus

This project uses Quarkus, the Supersonic Subatomic Java Framework.

If you want to learn more about Quarkus, please visit its website: <https://quarkus.io/>.

## Running the application in dev mode

You can run your application in dev mode that enables live coding using:

```shell script
./mvnw compile quarkus:dev
```

> **_NOTE:_**  Quarkus now ships with a Dev UI, which is available in dev mode only at <http://localhost:8080/q/dev/>.

## System naming and Docker ownership

Set `container.name` (environment variable `CONTAINER_NAME`) to a distinct, stable
name for each clinic, for example `clinic1` and `clinic2`. Clinic Compose files use
`${COMPOSE_PROJECT_NAME}` for this setting.

`NamingService` initializes the name once on the application startup event:

- Missing or blank: generates a UUID prefix of 16 hexadecimal characters.
- Up to 16 characters: uses the configured name directly, after trimming surrounding whitespace.
- Longer than 16 characters: uses the first 16 hexadecimal characters of its SHA-256 hash.

Use Docker-safe names such as `clinic1` or `fl-net-clinic1`. Startup logs show the
configured value, the resolution method, and the final `system_name`.
`BaseName`, container labels and volume labels use this same value. Lookups and
cleanup include `system_name`, so clinics sharing a Docker daemon cannot match
each other's workflow IDs. Direct cleanup also checks ownership before stopping
containers or deleting volumes.

An unset name changes on application restart. A configured name preserves the
namespace across restarts; changing it creates a new namespace. Finish active
workflows before upgrading from the previous naming scheme. Existing resources
without `system_name` are deliberately excluded from automatic cleanup; inspect
and remove those leftovers explicitly once they are no longer needed.

## Packaging and running the application

The application can be packaged using:

```shell script
./mvnw package
```

It produces the `quarkus-run.jar` file in the `target/quarkus-app/` directory.
Be aware that it’s not an _über-jar_ as the dependencies are copied into the `target/quarkus-app/lib/` directory.

The application is now runnable using `java -jar target/quarkus-app/quarkus-run.jar`.

If you want to build an _über-jar_, execute the following command:

```shell script
./mvnw package -Dquarkus.package.jar.type=uber-jar
```

The application, packaged as an _über-jar_, is now runnable using `java -jar target/*-runner.jar`.

## Creating a native executable

You can create a native executable using:

```shell script
./mvnw package -Dnative
```

Or, if you don't have GraalVM installed, you can run the native executable build in a container using:

```shell script
./mvnw package -Dnative -Dquarkus.native.container-build=true
```

You can then execute your native executable with: `./target/code-with-quarkus-1.0.0-SNAPSHOT-runner`

If you want to learn more about building native executables, please consult <https://quarkus.io/guides/maven-tooling>.
